# 9. Localization and English Terminology

> [简体中文版本](../docs_zh/i18n.md) · [Back to the English documentation index](./README.md)

AgentBox uses shared resource bundles to localize the renderer, Electron main process, preload-visible errors, native system dialogs, backup documentation, and built-in Agent and Skill copy. Simplified Chinese and English are currently supported.

## Language selection and persistence

- The application language type is `zh-CN | en-US` and is defined in [`src/shared/i18n/index.ts`](../src/shared/i18n/index.ts).
- When a Vault is created for the first time, an Electron `app.getLocale()` value beginning with `zh` selects `zh-CN`; every other locale, including a missing value, selects `en-US`. Chinese locales such as `zh-TW` currently use the Simplified Chinese bundle as well.
- The result is persisted in `AppSettings.language`. Subsequent launches use that value and do not track later operating-system language changes.
- If a legacy Vault has no `language`, [`normalizeAppSettings`](../src/electron/storage/settings-schema.ts) uses the current system-derived language as its fallback. The encrypted store detects that normalization changed the state and persists it, making this a one-time migration.

The main process sets the system-derived language before constructing the repository so initialization and early errors use the correct bundle, then switches to the stored language after unlocking the Vault. In the renderer, [`main.tsx`](../src/renderer/src/main.tsx) reads settings through preload and calls `setLanguage` before dynamically importing the React application. This prevents a flash of the wrong language during startup.

After the user changes **Settings → General → Appearance and behavior → Display language** and saves, both the renderer and main process update their active bundles. The renderer performs a lightweight reload after 150ms so module-level labels, title prompts, suggestions, and built-in Skill metadata are all materialized in the new language.

## Bundles and runtime API

| File | Responsibility |
| --- | --- |
| [`src/shared/i18n/locales/zh-CN.ts`](../src/shared/i18n/locales/zh-CN.ts) | Simplified Chinese translations. Keys are the English source copy |
| [`src/shared/i18n/locales/en-US.ts`](../src/shared/i18n/locales/en-US.ts) | Only the semantic "hatch" keys whose shared English text must distinguish different Chinese messages |
| [`src/shared/i18n/index.ts`](../src/shared/i18n/index.ts) | Locale resolution, active-language state, `MessageKey` typing, bundle lookup, and interpolation |
| [`scripts/localize-renderer.mjs`](../scripts/localize-renderer.mjs) | Key extraction, incremental draft translation `en → zh-CN`, reviewed overrides, and the `check` linter |
| [`scripts/migrate-i18n-keys.mjs`](../scripts/migrate-i18n-keys.mjs) | One-shot codemod that flipped the legacy Chinese-key scheme to English-source keys (kept for history; idempotency-guarded) |

**English source copy is the message key.** Author user-visible copy in English and pass it to `t()`:

```ts
import { t } from '../../shared/i18n'

t('Fetched {value0} models.', { value0: models.length })
```

Under `en-US`, a plain key renders as itself (after placeholder interpolation); under `zh-CN`, the reviewed Chinese translation from `zh-CN.ts` is used. `t(key, values)` looks in the active bundle, then falls back to the `en-US` hatch bundle, and finally returns the key itself — so an untranslated key degrades to readable English rather than showing a raw identifier. Placeholders may be named (`{count}`) or use the `{value0}` positional convention; the key and its Chinese value must preserve each placeholder name exactly. The `key` parameter is typed as `MessageKey` (`keyof typeof zhCN`), so typos, migration gaps, and references to removed keys surface at compile time. Format dates and numbers with `getLanguage()` and `Intl.DateTimeFormat` / `toLocaleString` instead of hard-coding `zh-CN`.

### Semantic hatch keys

Most copy uses its English text directly as the key. The exception is the small set of **semantic hatch keys** in `en-US.ts`, used when one English string must render as *different* Chinese messages. The canonical case is the Chinese Agent resume vocabulary — `继续`, `接着来`, `接着做` all read as English `Continue`, and `重试`/`再试一次`/`再次尝试`/`重新尝试` all read as `Try again`, but each must stay a distinct Chinese resume phrase so `agent-continuation` detection keeps working. One member of each group takes the plain English key (`Continue`, `Try again`); the others become semantic keys (`agentContinuation.continueVariant1`, `agentContinuation.tryAgainVariant1`, …) whose `en-US` value equals the shared English text and whose `zh-CN` value preserves the distinct Chinese. Add a hatch key only when a new same-English/different-Chinese collision appears.

## Extraction and generation script

The localization script scans renderer, Electron, and shared TypeScript sources plus built-in Skill definitions:

```powershell
# Extract keys (t() call-site literals + built-in Skill resource fields) and
# rebuild the Simplified Chinese bundle. Machine-translates only new keys.
node scripts/localize-renderer.mjs generate

# Lint: fail on Chinese outside t() or on a t() key missing from the bundle.
node scripts/localize-renderer.mjs check
```

`generate` collects every `t()` string-literal first argument (including both branches of a conditional) and every `name`/`description`/`systemPrompt`/Markdown-`content` literal of built-in Skills. It preserves existing Chinese translations and requests a machine-translated draft only for new keys. Resolution priority is: `reviewedZh` hand-reviewed override → existing translation → machine-translated draft normalized by `normalizeZhByContext` → the English key itself as a last resort. Semantic hatch keys must have an existing or explicitly reviewed Chinese value and are never machine-translated from their opaque identifiers. When new keys are present, the command may call an external translation service. Always review its diff; generated output is not automatically approved product copy.

`check` fails on (1) any Chinese string or JSX text outside a `t()` argument — including raw-Chinese fallback values that should be wrapped — and (2) any `t()` literal key absent from `zh-CN.ts`. Run it after every copy change.

Executable Skill files such as Python and Shell scripts are not UI copy and must never enter a resource bundle or machine translation. Localize only Skill names, descriptions, system instructions, and files where `kind === 'markdown'`. Code assets in built-in Skills must retain their executable meaning.

## Terminology

Use canonical English product and protocol terms in the source copy (the message keys):

- OpenAI: `Responses API`, `Chat Completions API`, `reasoning`, and `reasoning effort`.
- Anthropic: `Anthropic Messages API`, `adaptive thinking`, and `manual extended thinking`.
- MCP: `MCP server`, `MCP client`, `MCP tool`, `Streamable HTTP`, and `legacy HTTP+SSE`.
- OpenRouter: `provider`, `provider fallback`, `Zero Data Retention (ZDR)`, `native web search`, `latency`, and `throughput`.
- Security and backups: `plaintext`, `OS secure storage`, and `WinZip AES-256 (AE-2)`.
- Chat entities: use `conversation`; use `checkpoint` for Agent recovery and `skill archive` for a Skill ZIP.

Use the table below for new or deliberately revised copy. The key-flip migration intentionally preserved existing Chinese values byte for byte, so legacy entries in `zh-CN.ts` may retain older terminology until they receive a separate copy review. When the same English word needs different Chinese by context, add a semantic hatch key rather than forcing one translation.

| English key term | Canonical Chinese | Notes |
| --- | --- | --- |
| `provider` | 服务商 | preferred for new and reviewed product copy; legacy preserved translations may still use `供应商` |
| `conversation` | 会话 | `session` only for low-level protocol connections |
| `web search` | 网页搜索 | never `网络搜索`/`互联网搜索` |
| `reasoning effort` | 思考强度 | |
| `plaintext` | 明文 | never `纯文本` |
| `archive` / `skill archive` | 压缩包 | |
| `checkpoint` | 现场 | for Agent interruption recovery |
| `MCP server` | MCP 服务 | |

## Validation checklist

After changing user-visible copy, run:

```powershell
node scripts/localize-renderer.mjs generate
node scripts/localize-renderer.mjs check
pnpm typecheck
pnpm test
```

[`tests/i18n.test.ts`](../tests/i18n.test.ts) currently verifies that:

- Chinese-bundle keys carry no CJK and keep placeholder sets aligned with their Chinese values;
- the `en-US` hatch keys are a subset of the Chinese bundle and carry no CJK;
- English keys never use the disallowed machine-translation phrasings (`supplier`, `vendor`, `MCP service`, `prompt word`, `thinking intensity`, …);
- first-launch locale selection follows the documented rule;
- `setLanguage` changes bundles, dynamic interpolation works, plain keys render as themselves under English, and hatch keys resolve;
- executable built-in Skill assets never enter either bundle; and
- all five built-in Skills materialize with reviewed English names and Markdown instructions.

Code review must still check context, button length, English plurals, actionable error wording, and whether a new module-level constant requires the language-switch reload. Automated checks cannot replace those judgments.
